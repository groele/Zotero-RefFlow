# Zotero RefFlow 12.5.6

Released 2026-10-27.

Batch ownership and rollback history now live in `refflow-batch-journal-v1.json` inside the Zotero data directory. New imports no longer write internal batch markers or metadata snapshots into Extra. Opening the RefFlow reference pane, importing or undoing a batch migrates validated legacy records transactionally while preserving journal metrics and manual text.

- Keep shared-item, attachment, annotation, collection and manual-edit rollback protections. Restore batches after a process restart without Extra markers.
- Serialize local journal writes and retain stable item keys. Preserve unreadable, malformed or interrupted files; do not guess transaction outcomes or silently reset recovery evidence.
- Preserve manual Extra edits made while migration awaits child records. Updating older shared batches retains the latest-import order.
- Include the previously developed per-pane failure details, failed-DOI copying, targeted retries, keyboard navigation and tooltip lifecycle improvements.

## Validation and boundaries

310 unit tests, TypeScript, production build and release-tag policy checks passed. The exact production XPI passed 118 isolated Windows Zotero 10.0.6 native leaf scenarios: 6 local-journal migration, 2 same-profile restart, 16 batch retry, 31 ownership protection, 8 attachment/journal and 55 DOI/stage3/pipeline/dataflow scenarios. Nested suite wrappers are excluded.

Provider responses were controlled; PDFs were downloaded through the local test server. Main-profile installation, automatic-update scheduling/installation, Zotero 11, other systems and screen-reader output were not validated. Earlier ineffective fault injection and a fixture-induced nested-transaction timeout were corrected before final acceptance; host logs also contain connection/progress-window/timeout diagnostics, so the result does not claim an error-free host log.

The local journal does not sync through Zotero. Keep it with the matching library when moving devices; older add-on versions cannot read the new journal. If `pending: true` remains after an interrupted or failed finalization, preserve the file and verify the database outcome before recovery. Do not delete the journal or clear the marker by guessing.
